# Sync API Contract Skill

When the backend changes its API — new fields, removed fields, new endpoints,
renamed properties — this skill walks through every layer that needs to
change, in the right order, **without ever hand-writing or hand-editing a
generated DTO**.

**Read `CLAUDE.md`'s two hard rules at the top of this file before doing
anything here** — "NEVER hand-edit generated codegen output" and "Before
confirming a backend spec-change PR is correct, generate the actual DTOs".
This skill exists to operationalize those rules, not to work around them.

---

## Where things actually live (verify against `settings.gradle.kts` if this drifts)

- **DTOs** — `core/api/src/commonMain/kotlin/com/ivangarzab/kluvs/api/models/` —
  100% generated by the OpenAPI Generator from `core/api/openapi.json`. Every
  file carries a "do not edit" header. **Never** hand-write or hand-edit
  anything here, and never add hand-written files into that directory.
- **Mappers** — `core/data/src/commonMain/kotlin/com/ivangarzab/kluvs/data/remote/mappers/`,
  one file per entity (`MemberMappers.kt`, `ClubMappers.kt`, etc.), each
  exposing `fun <SomeDto>.toDomain(): <DomainModel>` extension functions.
  This is the one layer that's always hand-written — it's where the generated
  DTO shape gets bridged to the domain model shape.
- **Domain models** — `core/model/src/commonMain/kotlin/com/ivangarzab/kluvs/model/`
  — camelCase, no serialization annotations, `kotlinx.datetime` types for dates.
- **Services / RemoteDataSources / Repositories** — `core/data/src/commonMain/kotlin/com/ivangarzab/kluvs/data/remote/api/`,
  `.../remote/source/`, `.../repositories/` — only touched when an endpoint's
  signature or a new endpoint is involved, not for a plain field change.

## Two different situations — pick the right one

### A. A backend spec change hasn't shipped yet (you're reviewing a candidate PR / branch)

Follow `CLAUDE.md`'s documented verification steps exactly — pull the
candidate `docs/openapi.json` from `kluvs-backend` via `git show` (never
check out or switch branches in backend's working tree), copy it to
`core/api/openapi.json`, run `./gradlew :core:api:openApiGenerate --quiet --console=plain`,
read only the specific generated `.kt` file(s) for the changed types, then
revert `core/api/openapi.json` and delete `core/api/build/generated/openapi`.

**Also revert any files under `core/api/src/commonMain/kotlin/.../api/models/`
that the generate step modified** (`git status` will show them) — this
repo's `openApiGenerate` task writes generated output directly into that
committed source directory, not just `build/generated/openapi`, so the
documented cleanup in `CLAUDE.md` is incomplete on its own; check `git status
core/api` after generating and `git checkout --` anything it touched before
moving on.

Use this when double-checking a backend PR is correct before telling the
user so, or when doing parallel-track mobile work against a not-yet-shipped
contract (see `CLAUDE.md`'s "temporary interim types" exception for that
specific case).

### B. A backend spec change has already shipped and regenerated a real PR here

The sync from `kluvs-backend` → `kluvs-api` → `kluvs-mobile` is a live,
three-hop GitHub Actions chain today (see `../CLAUDE.md`'s "API Contract
(`kluvs-api`)" section for the full trigger/dispatch details). Once a backend
change is released (merged to backend's `main`, not just `develop`), a bot
PR titled `chore: regenerate api models from spec <sha>` (branch
`chore/regenerate-api-models`) appears against **this repo's `develop`**,
containing exactly the regenerated `core/api/openapi.json` +
`core/api/src/commonMain/.../api/models/**` diff — nothing else.

For that PR: **read the diff directly** (no need to run the generator
yourself, it already ran in CI) and check every field the ticket's contract
promised actually shows up with the right nullability/type — the same
sibling-keyword-dropping gotcha `CLAUDE.md` warns about (`nullable: true`
next to a `$ref`) applies here too, so a structurally-valid spec can still
produce a DTO that's missing something a hand-read of the JSON would have
implied was there.

## After the DTO is confirmed correct: propagate to the rest of the app

For each affected entity, determine what else needs to change:

| Change type | Layers affected |
|---|---|
| New field added to response | Mapper → domain model (DTO is already regenerated) |
| Field removed from response | Mapper → domain model → check Room entity |
| Field renamed | Mapper only (DTO's `@SerialName` already reflects the new wire name) |
| New endpoint added | Service → RemoteDataSource → Repository → Koin registration |
| Endpoint removed | Service → RemoteDataSource → Repository → Koin cleanup |
| Request body changed | Already reflected in the regenerated Request DTO — update the Service call site that builds it |
| Response type changed | Mapper → domain model |

Present a clear impact summary before touching any file:

```
## API Change Impact

### Changed: Member endpoint (already regenerated in core/api)
- Added field: `MemberDto.rating` (Float, nullable)

### Files to update:
1. MemberMappers.kt — map `rating` to domain
2. Member.kt (domain model) — add `val rating: Float? = null`

### Room cache — flagged:
MemberEntity caches member data. If `rating` should be cached locally,
a Room migration is required (see migrate-room-db skill).
Do you want to cache this field? [yes / no / skip for now]
```

Wait for user confirmation before writing any files.

Apply changes in this order — each layer depends on the one before it:

1. **Domain model** (`core/model`) — the target shape everything maps to
2. **Mapper** (`core/data/.../remote/mappers/`) — bridge the (already
   regenerated) DTO to the updated domain model
3. **Service** (`core/data/.../remote/api/`) — only if endpoint signature changed
4. **RemoteDataSource** (`core/data/.../remote/source/`) — only if a new method is needed
5. **Repository** (`core/data/.../repositories/`) — only if new capability is exposed
6. **Koin** (the relevant `*Module.kt`) — only if new classes were added

## Room cache handoff

After all data layer changes are applied, evaluate whether any changed field
is stored in a Room entity (`core/database/src/commonMain/.../entities/`).

If yes, state clearly:
> "The `{field}` field on `{Entity}` needs a Room migration.
> Refer to the **migrate-room-db** skill to complete this step."

Provide the migration context: what changed, old schema, new schema.
Do not write migration files in this skill — that belongs to `migrate-room-db`.

## Conventions to follow

**Mappers** — extension functions on the generated DTO type, `toDomain()` pattern:
```kotlin
fun MemberDto.toDomain(): Member = Member(
    id = id.toString(),
    name = name,
    rating = rating
)
```

**Domain models** — camelCase, no serialization annotations, use `kotlinx.datetime` types for dates:
```kotlin
data class Member(
    val id: String,
    val name: String,
    val rating: Float? = null
)
```

**Never** hand-write or hand-edit anything in `core/api/.../models/` — see the
hard rule at the top of `CLAUDE.md`.
**Never** add serialization annotations (`@Serializable`, `@SerialName`) to domain models.
**Never** add business logic to DTOs.
**Never** skip the mapper — domain models must not reference DTO types.
